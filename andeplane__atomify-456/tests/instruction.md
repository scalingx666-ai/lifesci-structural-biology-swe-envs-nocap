# Issue

**Title:** Scope storage key scans to the project and mark runs failed on full storage

## Description

_Requested by **Anders Hafreager** · [project thread](https://claude.ai/code/project/chan_01G7VSoPZwxUhEt8N3Ft8nF9?thread=cmsg_01G7VSoPZwxUhEt8N3Ft8nF9KjvR2puXtm8nCym4ZnStxL)_

**Before:** `ContentsProjectStorage` called `files.keys()` over the whole "JupyterLite Storage" database for every list, rename, remove, deleteProject, createProject and listProjects, so each of them got slower as the library grew. Renaming a directory moved one key at a time (set new, remove old), so closing the tab partway left a half-moved directory. A quota error while copying run outputs only produced a generic "Could not copy run outputs" toast, the run was still marked `completed`, and a quota error on the final run.json write left `activeRun` stuck. ADR-001's promised "storage full" handling did not exist. Record `size` was the UTF-16 string length.

**After:** Key scans only cover the directory being worked on, plus a top-level skip-scan for the library. A rename writes every new key before removing any old one, so an interrupted rename leaves a duplicate and never loses data. A run that hits the quota is marked `failed` with "Browser storage is full — free space in Settings > Storage." and keeps its partial outputs. A notice names the project, and the rest of the queued sweep is stopped. `size` now matches JupyterLite.

**How:** `KeyValueStore` gets two optional methods, `keysWithPrefix` and `topLevelNames`. Callers go through helpers that fall back to filtering `keys()` when a store doesn't have them. The localforage backend answers both with raw IndexedDB key reads on the same db/object store localforage writes to:
- `keysWithPrefix` uses `getAllKeys(IDBKeyRange.bound(prefix, prefixSuccessor, false, true))`.
- `topLevelNames` uses a cursor that jumps past each `name/` subtree to `name0`.

Only reads use raw IDB. Every write still goes through localforage, so the record format JupyterLite reads is unchanged. The raw connection opens without a version after `ready()` (so it never creates or upgrades the db) and closes on `versionchange`, the same way localforage's own connections behave. `deleteProject`/`remove` delete project.json and directory records last. Quota errors (`QuotaExceededError`, Firefox `NS_ERROR_DOM_QUOTA_REACHED`, legacy code 22, also when nested in `cause`) are turned into a typed `StorageFullError`. For `size`, I checked `BrowserStorageDrive.save` in `@jupyterlite/services@0.8.6` (the version this repo pins): it stores the UTF-8 byte count of the stored content, and for json it measures the compact `JSON.stringify`. The record builder now does the same. Adds `fake-indexeddb` as a devDependency so the raw IDB path is tested together with localforage.

Not covered: a quota error during the pre-run snapshot or the first run.json write still throws out of `executeNextRun`, as it did before. Handling it would mean re-indenting a large block of projects.ts, which another PR is splitting.

**Testing:** `npm run typecheck`, `npx vitest run` (43 files / 504 tests pass). New tests:
- `kv.test.ts`: localforage format compatibility, prefix range query, skip-scan, not blocking a localforage store upgrade, quota wrapping, ContentsProjectStorage end to end on fake IDB.
- Prefix scoping with no `keys()` calls, the `keys()` fallback, rename ordering and the interrupted-rename duplicate, delete ordering.
- UTF-8 `size`.
- Integration: storage-full run marked failed, partial outputs kept, sweep stopped.
