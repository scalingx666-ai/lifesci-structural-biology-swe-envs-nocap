# Issue

**Title:** Fail runs cleanly when the engine worker crashes

## Description

Before: if the engine Web Worker crashed (wasm abort, OOM, uncaught error), `LammpsWorkerProxy` never found out. It had no `onerror`/`onmessageerror` handler, so pending `runFile` promises never settled and the UI stayed "running" forever. Only `snapshotWorkdir` had a 60s fallback.

After: a crash fails the in-flight run straight away with "The simulation engine crashed: <message>". The message shows up in the console output, the run's `run.json` is marked `failed` with that error, the sidebar engine chip says "Engine unavailable: … Reload the page to restart the engine.", and the run buttons are disabled until you reload.

How: the proxy now treats `worker.onerror` and `worker.onmessageerror` as fatal. It rejects all pending runs, snapshots and `load()`, terminates the worker, and marks itself crashed. After that, `runFile` and `snapshotWorkdir` reject immediately and fire-and-forget commands are dropped. It passes the message to the existing `onError` path and to a new `onCrash` hook. `Simulation.tsx` uses `onCrash` to set `app.engineError`, and `Shell` now treats an engine error as not ready, so the existing sidebar chip appears. The `run` thunk now uses an `Error`'s `.message` (no `"Error: "` prefix) for `lastError` and `run.json`. The worker and the message protocol are unchanged: the worker already answers every `runFile`/`snapshotWorkdir` even when they throw, and uncaught errors reach the main thread through `onerror`.

Testing: `npm run typecheck`; `npx vitest run` (43 files, 493 tests pass). New `src/wasm/LammpsWorkerProxy.test.ts` uses a fake Worker to check that a pending run rejects, later runs reject at once without posting, pending and later snapshots reject (and the timer is cleared), `messageerror` counts as fatal, `load()` rejects, and the healthy path still resolves. A new integration test in `projects.integration.test.ts` checks that a crashed run ends as `failed` in `run.json` with the crash message.
